# PR, review, and squash-merge cycle

- Unless the user specifies another stopping point, implement, validate, open/update a PR, review, fix findings, and squash-merge. Use a `codex/` branch, never commit directly to `main`; preserve unrelated local work and include only task changes.
- After validation, push and open/update the PR with a clear description and results. Obtain independent review of its current diff through a PR reviewer or review subagent; fix actionable findings, push, and recheck using the progress checkpoints below. Unresolved findings remain merge blockers while work continues.
- Merge only when the latest PR commit is reviewed, required CI passes on its integration with the latest target branch, required approvals are satisfied, and the PR is mergeable. If the target advances, update the PR and validate the combined tree. Keep `main`'s strict required `checks` protection and administrator enforcement enabled. Report pending/unavailable reviews or checks as blockers; never bypass them.
- Immediately before merging, recheck `main`'s HEAD and CI status and all merge requirements above. Wait for every unfinished `main` CI run; never cancel one to unblock a merge or let a merge cancel/supersede it.
- Before waiting or yielding, refresh the exact blocking PR, review, or CI run and record its identifier and current state. Continue immediately when blockers are resolved; recheck on every wake or resume instead of carrying forward stale waiting status. Arrange supported completion monitoring for each pending dependency, including separate `main` runs; a PR-only watch does not cover those runs. If no supported wake-up covers a dependency, report the monitoring gap and its link explicitly rather than claim it is being watched. Stop obsolete watches after the task completes.
- Squash-merge into the target branch without further confirmation unless later user instructions or repository policy require it. Verify the merge; report the PR link, squash commit, and validation results. Sync the local target only if existing local work is preserved.

## Progress and stop conditions

- State the requested outcome and the checks needed to finish before implementation. Take the smallest path to that outcome. Do not add unrelated fixes, audits, refactors, or polish; report follow-up ideas separately. Reassess against the original outcome after each failed attempt or review round.
- After three unsuccessful attempts on the same blocker, or an initial review plus two fix/review rounds without acceptance progress, reassess the approach. These are checkpoints, not lifetime limits or reasons to abandon the task. Carry attempts and evidence across agents, tool changes, pushes, handoffs, and resumes; do not relabel a failed approach to hide its history.
- At a checkpoint, record why prior attempts failed, choose a materially different next step supported by evidence, and define an observable result that will confirm or reject it. Prefer simplifying or removing failed experiments over adding layers. Continue autonomously within the authorized scope with a finite next plan; no new permission is needed solely because a checkpoint was reached. If a repair is not yet supported, use focused diagnosis to establish the next hypothesis. Do not rerun unchanged failures hoping for green, reopen settled decisions without new evidence, or review an unchanged diff again. Once required checks pass and the current diff has a clean review, proceed to the merge gates rather than invent more work.
- Give each delegate a bounded task, expected result, and the shared attempt history and next checkpoint. Delegates return findings or a blocker at that boundary; they must not recursively delegate or start their own review/fix cycle. The coordinating agent chooses the next evidence-led step and remains responsible for completing the original outcome.
- Stop an unproductive approach, preserve the work, and continue useful authorized diagnosis or implementation. Hand back as blocked only when a concrete required input or external dependency prevents further useful work; report what is complete, the exact blocker, attempts and evidence, and what must change. An attempt count alone is not a blocker. Make routine technical decisions without waiting for the user. Do not bypass checks, required approvals, or merge unresolved work. For pending external dependencies, use supported completion monitoring rather than polling loops or replacement jobs; an unchanged wake is not progress and must not restart the same failed approach. Resume dependent work when the dependency changes.
